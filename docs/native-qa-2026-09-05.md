## Android build memory finding

The generated Gradle defaults (`-Xmx2048m -XX:MaxMetaspaceSize=512m`) failed
during `lintVitalAnalyzeRelease` with `Metaspace`. The failed daemon kept a cache
lock; only that identified build process was terminated before retrying.

The successful local build used this command from `apps/mobile/android`:

```sh
SENTRY_DISABLE_AUTO_UPLOAD=true \
SENTRY_DISABLE_NATIVE_DEBUG_UPLOAD=true \
SENTRY_AUTH_TOKEN= \
EXPO_NO_TELEMETRY=1 NODE_ENV=production \
./gradlew :app:assembleRelease \
  -PreactNativeArchitectures=arm64-v8a \
  '-Dorg.gradle.jvmargs=-Xmx4096m -XX:MaxMetaspaceSize=1536m' \
  --no-daemon --max-workers=2 --console=plain
```

This was a per-command override, not a persistent config change. Future local
Release builds may need the same override; a clean CI build with its actual
runner limits is still required.

## Local update-check diagnosis at commit aa0de60

Read-only inspection of the installed iOS QA application's persistent
`expo-updates` log confirmed repeated HTTP 400 responses:

```text
"channel-name": Required
```

The installed application's `Expo.plist` enables updates and points to the
configured EAS Update project, but has no `EXUpdatesRequestHeaders` entry and
therefore no `expo-channel-name`. The generated iOS source plist and Android
manifest also lack this header. The confirmed runtime failure is on iOS;
Android has the same configuration risk but its update request was not repeated.

This QA binary was built directly with native build tools, outside an EAS Build
profile. `apps/mobile/app.config.js` preserves the base update configuration
without adding a channel. Although `eas.json` declares `preview` and `production`
channels, these profile values are not injected by a direct Xcode/Gradle build.
Expo's [standalone service documentation](https://docs.expo.dev/eas-update/standalone-service/)
confirms that non-EAS builds require explicit channel configuration.

The signed-release script uses EAS Build with `--profile production`, whose
channel is configured. This local failure does not establish that a distributed
production binary is affected; no such binary or remote channel was inspected.
The `e2e-test` profile also lacks a channel and should have an explicit OTA policy
before it is used for a release-mode test build.

Recommended follow-up: introduce an explicit local-QA/E2E build mode with OTA
