## Android build memory finding

The generated Gradle defaults (`-Xmx2048m -XX:MaxMetaspaceSize=512m`) failed
during `lintVitalAnalyzeRelease` with `Metaspace`. The failed daemon kept a cache
lock; only that identified build process was terminated before retrying.

The successful local build used this command from `apps/mobile/android`:

```sh
SENTRY_DISABLE_AUTO_UPLOAD=true \
SENTRY_DISABLE_NATIVE_DEBUG_UPLOAD=true \
SENTRY_AUTH_TOKEN= \
EXPO_NO_TELEMETRY=1 NODE_ENV=production \
./gradlew :app:assembleRelease \
  -PreactNativeArchitectures=arm64-v8a \
  '-Dorg.gradle.jvmargs=-Xmx4096m -XX:MaxMetaspaceSize=1536m' \
  --no-daemon --max-workers=2 --console=plain
```

This was a per-command override, not a persistent config change. Future local
Release builds may need the same override; a clean CI build with its actual
runner limits is still required.

## OAuth follow-up after commit be9ef3a

### Apple cancellation defect

The installed Expo Apple Authentication implementation returns the native
`ERR_REQUEST_CANCELED` code with a human-readable message such as
`The user canceled the authorization attempt`. The application previously
searched the message for the code, causing normal cancellation to be treated
as an error and reported to Sentry. The handler now checks the error object's
`code` with null/type guards. It no longer mistakes unrelated errors whose
messages mention that code for cancellation.

The existing cancellation test was corrected to use the native error shape.
Three additional tests cover a plain native rejection object, an unrelated
error code, and a null rejection. Three tests failed before the fix and all
ten Apple-auth tests pass after it. This is supported by the installed SDK
source and the [official Expo cancellation example](https://docs.expo.dev/versions/latest/sdk/apple-authentication/).
It has not yet been exercised in a newly built iOS binary or with an Apple ID.

### Google callback regression coverage

Four additional test cases cover browser dismissal, failure to open the browser,
a provider-error callback and incomplete callback tokens. They verify that
invalid callbacks do not create a session and that callback ownership is
released for subsequent attempts. The successful-flow test also checks the
custom redirect scheme and `skipBrowserRedirect` configuration.
