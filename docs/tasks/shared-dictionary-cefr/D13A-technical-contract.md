## 2. Storage and identity

Add `words.dictionary_content_mode` with `legacy` default and `follow` target.
This name is proposed; D13A.3 must implement an equivalent explicit discriminator.
Legacy rows retain their current semantics until reviewed conversion. A following
row has an entry ID, stable personal word ID, owner, collection and learning state.
The existing revision ID is retained temporarily as adoption provenance/legacy
compatibility; it is not the authority for the current following analysis.

The common entry owns its meaning and immutable published revisions. Publication
updates one head, not every personal row. Personal content version describes
reference/mode changes; head event sequence describes common content changes.
No following row may acquire linguistic overrides, detach on analysis, or treat
legacy fallback columns as editable authority. Keep those columns and protected
originals through D14; their presence during transition is not a new private feature.

Entry identity is language + reviewed meaning/sense identity, not spelling or an
AI similarity score. Preserve the existing legacy personal-card uniqueness limit
while old clients remain supported. Different senses must never merge to evade it.
Cache aliases and official-pack mappings require verified entry/revision identity.
Create a new common entry only through an explicit resolved-meaning operation;
`persist_canonical_dictionary_analysis_v1` currently creates a new entry, so it is
not the publisher for reanalysis of an existing entry.

Use an additive protected meaning anchor (neutral gloss plus disambiguating
examples/source) for reanalysis validation. Generated analysis cannot overwrite
that anchor. Entries without a verified anchor require meaning review before
reanalysis can publish; existing analysis remains readable. This is a technical
validation hold, not mandatory administrator approval of every permitted request.

## 3. Read and synchronization contracts

Add dictionary capability/effective-content protocol 2 and web review snapshot v3.
The capability advertises supported read/command versions and enabled behavior
explicitly; it must not reinterpret protocol 1 capability as protocol 2 support.
A batch response contains personal references, applied revision IDs, common revision
objects deduplicated by revision ID, head event sequences and a snapshot watermark.
Ownership is checked on every requested personal word. Published common revisions
can be public-readable; operation inputs, private originals and user state cannot.

Use decimal strings for new BIGINT cursor/sequence fields. Never compare sequences
as lexicographic strings or JavaScript floating-point values. Existing protocol 1
numeric serialization must remain within its safe range or fail explicitly.
The existing transactional `dictionary_content_changes` log and singleton delivery
cursor are the ordering authority; do not create a second publication log.

Read the batch/snapshot in one database snapshot. Validate all revision dependencies
before atomically committing affected cache/reference state and acknowledging that
page's watermark. Repeated pages are safe. Missing/corrupt content retains the last
valid cached revision and refresh debt; it must not be reported as fresh success.
Progress synchronization remains independent of recoverable dictionary failures.
Bound and batch requests, avoid one fetch per card, and prune only revisions unused
by references, active sessions, pending work and retention policy.

A publication is visible after successful online synchronization. Offline clients
keep cached content. Active review sessions capture immutable content/revision IDs
and finish consistently; newly started sessions use the latest fully hydrated state.
A next session while still offline may legitimately use the old cached version.
Account changes isolate owner queues/cursors and references; public revision cache
sharing cannot expose private cards or learning.

## 4. Authorization, operation lifecycle and publication

Existing `AccessLevel` has only `read_only` and `full_access`. There is no trusted
application-administrator membership in the inspected schema. Add a private,
service-managed administrator membership table keyed by verified Auth user ID,
with enabled state and audit metadata. Do not add a client-writable enum/claim or
infer administrators from email. Initial live grants need named IDs and release
scope; none are granted by this design.

Analysis permission is verified user AND (`full_access` OR active administrator).
A read_only account that is explicitly an administrator qualifies via that role.
Unauthenticated, ordinary read_only and revoked callers fail closed. Check at
acceptance and again in the publication transaction, using current trusted state.
Only administrators may invoke rollback; both roles use the same analysis quota.
Browser/mobile callers never receive service-role credentials or direct head writes.

Proposed authenticated command input: `operation_id`, `entry_id`,
`expected_revision_id`, `expected_head_sequence`, and protocol version. Derive actor
from the verified session; do not accept user IDs or arbitrary private card content
as provider prompts. New-word resolution is a separately typed operation with a
reviewed identity outcome. Return a durable actor-scoped receipt, not a private
provider response belonging to another user.

Persist private operations keyed by actor + operation ID with request hash,
expected head, status, validator/provider metadata, quota accounting, dispatch
intent and result hash. Same key/same request returns the receipt; changed request
returns `operation-payload-conflict`. Reserve an active entry lease/fencing token
and one quota slot atomically. A concurrent different request for the same entry
returns `analysis-in-progress` without another provider call or quota increment.
Reuse the existing quota counter in that transaction; its current per-request
function alone does not make network retries idempotent.

Lifecycle: accepted -> dispatching -> validating -> published, rejected,
head-conflict, authorization-revoked, provider-failed or provider-outcome-unknown.
Commit dispatch intent before the external call; journal a returned result before
publication. No database transaction spans the provider request. Retry publication
from the durable result without paying for another analysis. A crash with unknown
provider outcome is not automatically redispatched: reconcile provider evidence,
or require an explicit new attempt. A lease timeout alone cannot prove a paid call
did not occur. Fencing prevents late workers publishing; it cannot guarantee exactly
one physical provider invocation without provider idempotency support.

A quota slot represents one accepted provider attempt, including failed attempts;
replays, concurrent rejection and follower hydration consume no extra slot. Reuse
configured limits; D13A.8 must record the actual limit and estimated cost rather
than silently increasing it. CEFR remains disabled and never starts implicitly.

Validate schema, required data, content limits, safe media, protected identity and
same meaning before publication. Failed/meaning-changing results leave the head
unchanged. Semantic checking is imperfect: D13A.7 requires positive/negative sense
fixtures and measured failure review; a language-model confidence score alone is
not acceptance. Low-confidence results enter review, not global publication.

Add explicit provenance for automated validation (validator version, provider/model,
input/content hashes, initiating actor, timestamp and validation outcome). Existing
`reviewed_by`/approved source requirements must not falsely label machine validation
as human review. Extend constraints/triggers additively, preserving original human
source evidence and immutable historical revisions. Public provenance redacts actor
identity and prompts. Protected-source approval remains separate from merely having
permission to invoke analysis; arbitrary private originals are not approved sources.

The final short transaction checks permission, operation fencing/status, exact
expected head and source/validation evidence, inserts the immutable revision,
updates the head, records the existing delivery event and marks the receipt published.
Any failed check rolls back all these writes. A no-change content hash can complete
as an explicit no-change receipt without a new revision/event. Never overwrite a
newer head with a stale analysis. Retry after a lost HTTP response returns the same
publication receipt. Operation logs are owner-readable through bounded RPCs and
administrator-auditable, not exposed by public table access.

Privileged SQL must use a pinned search path, qualified names, explicit execute
revocations and narrowly granted wrappers with in-function ownership/role checks.
Service-role access does not itself authorize an arbitrary caller's request. See
[Supabase functions](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/database/functions.mdx)
and [RLS guidance](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/database/postgres/row-level-security.mdx),
retrieved through Context7 during this checkpoint.

## 5. Compatibility, import and rollback

Keep protocol 1 and legacy rows working during coordinated rollout. A version 1
adapter for following rows must return the actual current revision reference with
matching content and empty overrides, in its existing strict response shape.
The historical `pinned` label remains a wire compatibility label only. D13A.7 must
prove this with exact embedded/build85 and OTA parsers plus SQLite dependencies;
until proven, do not convert a cohort relying on that client.

Reject version 1 private-edit/detach/resolve-conflict operations on following rows
before mutation with a recognized upgrade/reconciliation outcome. Preserve pending
payloads; never silently clear them, publish them globally, or convert a following
row back to private. Learning-only writes continue through compatible paths. A
client whose sync pipeline blocks learning behind such a command must reconcile
or upgrade before cohort conversion. Unknown offline queues block that cohort,
not all development. Test old full-row writes against the existing content guard.

New shared-reference import intents include verified entry identity and source
manifest provenance. The adopted revision is recorded for audit; following reads
then use the current published head. Official package version/checksum still refers
to the immutable original manifest. Shared collection import copies references and
creates fresh personal learning, never the source owner's learning or overrides.
Do not silently reinterpret already queued protocol 1 import intents.

Content-only export v1 stays a portable snapshot. A version 2 export may include
published entry identity, exported revision/hash and analysis for offline portability,
without owner IDs, progress, private history or unpublished references. Imported IDs
are untrusted hints requiring server verification. Foreign/unresolved content stays
in a protected import-review disposition; it is not automatically published or
converted into a permanent personal override. Preserve legacy import recovery data.

Administrator rollback selects a previously published revision of the same entry,
with expected current head/sequence and audited reason. Moving the head backwards
emits a NEW delivery sequence via the existing trigger; clients order by sequence,
not revision number. Learning never rolls back with content. Do not use global
read-disable or embedded OTA rollback as the default: build85 compatibility and the
already repaired parser make those unsafe assumptions. Release rollback uses a
verified compatible client/backend package and selective reference restoration.

## 6. Old-card transition

The October4 rehearsal found 2914 cards and zero safe automatic matches. Retain
that result. D06 text matching that ignores media and produces personal overrides
is not valid for this target. Exact means all analysis fields, including media;
otherwise require a reviewed same-meaning mapping with an approved field-level diff.

Mapping v2 binds personal word ID, owner, existing mode/reference/content version,
full original content hash, collection/deletion state, target entry/head/sequence,
reviewed identity evidence, approved changed fields and immutable decision hash.
No unreviewed private text/examples/images may become common source material.
Disposition is exact-link, approved-diff-link, ambiguous, missing, private-review,
stale or excluded. Unresolved rows remain usable under legacy semantics, explicitly
outside completed migration; they cannot justify D14 deletion.

Before apply, protect originals and reconcile current device queues and live delta.
Reuse bounded batches (default50, max100), row locking, expected-state fingerprints
and durable per-row receipts. Lock/check target heads in the same transaction so a
new publication cannot change the approved delta under apply. Stale mapping skips
with reason; it does not guess. Dry-run and apply use the same classification.
Stable personal IDs, ownership, collections, SRS, review history and pending learning
operations are invariant. Learning fields do not enter a stale-content fingerprint
and must never be overwritten from the snapshot. Interrupted retries return receipts.

Migration rollback restores only reference/mode/content fields owned by the matching
migration receipt, conditional on no subsequent reference/content change. Concurrent
learning remains untouched. Changed rows are skipped for reconciliation. Protected
originals stay private and recoverable; do not restore a full database backup over
later reviews. D13A.6 must prove apply + new review + rollback in real PostgreSQL
and SQLite fixtures, including interrupted batches and deletion races.
Content versions increase monotonically during compensation; never restore an old
version. An originally absent legacy state becomes the protected original effective
fallback in the retained new state. Later shared head/sequence changes are also held.
Selective compensation may operate with capabilities disabled without enabling them.
Disposable SQLite rehearsal is not runtime delivery; authoritative server versions,
watermarks and actual device queues require D13A.7/8 qualification.

## D13A.3 authority/journal checkpoint (October 10, local only)

Migration `20261010100000_add_dictionary_analysis_operations.sql` adds private
administrator membership, immutable human-verified meaning anchors and their
protected pointers, actor-scoped operations, monotonic entry leases and immutable
raw-result journals. There are no seeded live memberships/anchors. The existing
`read_only`/`full_access` enum and human source/revision approval constraints remain
unchanged. Anchored sources also become immutable, even before a revision uses them.

`accept_dictionary_analysis_v2` takes only the five reviewed command fields. Actor
comes from `auth.uid()` and must exist in Auth. The request is hashed using UTF-8
PostgreSQL JSONB text, with exact-key replay serialized before entry locking. It
reserves one existing gemini-analysis counter unit and a fence in one transaction.
Defaults match existing application configuration: 10 attempts per 60 seconds;
there is no increased limit. Busy outcomes have no fabricated receipt/quota charge.
A separate `analysis_operations_enabled` flag defaults false. Capability2 still
advertises `shared_analysis_enabled=false` because publication is not implemented.

Service-only RPCs start dispatch once, journal a bounded (256 KiB) raw JSONB result,
and record failure/unknown outcomes. Start rechecks current permission, exact
revision plus decimal head sequence and the protected anchor. Its first committed
transition returns a shared identity/anchor payload; retries return `dispatch=null`.
Provider/model/input hash metadata conflicts fail closed. A lost dispatch reply
cannot authorize another physical call. No actual provider integration is included.
The input hash is trusted worker metadata; the following checkpoint must bind the
validator's protected input/result/content hashes before publication.

Leases last five minutes. Expired accepted work may be replaced by an explicit new
operation with a higher fence. Expired dispatched work is durably quarantined,
never redispatched automatically. Busy after expiry is returned rather than raised
so the quarantine transition commits. A known-failure reconciliation requires a
service-supplied evidence SHA256. Late responses, including those received after
unknown was already persisted, are journaled but remain quarantined. Reconciliation
of a quarantined journaled result is deliberately held until validation/publication
support is implemented; it cannot currently publish or release its entry lease.

Owner receipt lookup and history (maximum 100, timestamp/operation cursor) return
only receipt metadata, not actor identity, prompts, provider IDs or raw responses.
Enabled administrators may explicitly audit another actor's bounded history.
Operation/result data cascade on Auth deletion without preventing account removal;
the entry fence remains and can be reused. Service-role workers cannot directly
update operation/lease/result tables; they use narrowly granted RPCs.

Remaining D13A.3: immutable automated validator provenance, safe human/machine
source distinction, explicit late-result reconciliation, final permission/fence/head
checks and atomic publish/no-change receipts using the existing delivery event;

workflow, actual rollback integration and device/corpus acceptance remain D13A.4–7.

## D13A.3 validation/publication implementation (October 10, local only)

Migration `20261010110000_add_dictionary_analysis_publication.sql` adds a
default-off publication flag, an empty validator-policy registry, immutable
validation evidence and immutable publication permits. Service workers may
register a qualified version/policy hash and change only its enablement, not its
content or media policy. No real policy or grant is seeded. Both analysis flags
must be enabled before a new publication; capability2 remains unavailable until
the later workflow/client integration. CEFR stays disabled.

Validation packets bind the protected anchor, dispatch input and journaled result
hashes to one operation/fence and qualified policy. Accepted content must equal
the journaled candidate, pass strict field/nested-array/UTF-16 length limits,
match entry lemma/POS/article and use only policy-approved public HTTPS media
paths without query credentials or traversal. Canonical content and CEFR hashes
are recomputed using the existing canonical JSON serializer; raw JSONB result
hashes are a different contract. Rejected or uncertain decisions persist evidence
and release the lease without changing the head. Database checks can downgrade an
accepted worker claim but cannot prove semantic equivalence. The actual meaning
evaluator and measured positive/negative fixtures remain D13A.4/7.

Explicit service-only reconciliation accepts the exact already-journaled result
and a durable evidence hash. Matching retries replay; changing that evidence
conflicts. It rechecks current authority and dependencies, returns quarantined
late work to validation and never creates a new dispatch/quota charge. Unknown
work without a journaled result cannot use this route.

Publication locks Auth before entry/operation/lease rows and holds SHARE locks on
current authority/policy/runtime rows. Existing head and anchor triggers serialize
against the parent entry lock. Both permission and expected revision plus decimal
head sequence are rechecked; restoring an old revision does not hide an intervening
head event (ABA). PostgreSQL row-lock behavior was checked against
[PostgreSQL16 locking documentation](https://www.postgresql.org/docs/16/explicit-locking.html)
through Context7. A transaction-scoped XID8 permit precedes its source and revision
inserts, with deferred foreign keys. Machine source/revision guards accept only
that permit and exact immutable validation. Revision, source, head, existing
delivery event and durable receipt commit together. Exact equal content/hash
returns a no-change receipt without a new source/revision/event. Lost-reply replay
returns the stored receipt even after authority or policy revocation.

Machine sources use `machine_validated` and keep human `reviewed_by`, `reviewed_at`
and `approved_content_sha256` empty. Machine published revisions likewise have no
human review timestamp. Human published/retired revision inserts still require
matching approved human provenance and `reviewed_at`. Historical sources/revisions
remain immutable. Auth deletion removes private operation/result journals and
redacts only the actor UUID in retained validation evidence, preserving the shared
revision/provenance. Evidence and permits cannot be inserted/mutated directly by
ordinary clients or service workers; only guarded wrappers write them.

`get_dictionary_revision_provenance_v2` returns at most500 deduplicated revisions
with method, validator/provider/model (null for human review), content hash and
verification timestamp. Published revisions are readable by authenticated users;
retired revisions require the caller's pinned personal reference, while drafts
remain hidden. Actor/operation/source/anchor IDs, input evidence, prompts and raw
provider responses remain private. Domain strict parsers cover validation packets
and this redacted response without extending existing strict revision wire shapes.

This checkpoint supplies dormant transaction/provenance contracts. Provider
