# D13A.8 rollback and containment plan — October 23, 2026

Status: prepared only, no rollback executed or authorized. Source/target binding is in
[the release manifest](D13A.8-release-packet-20261023.json). Actual compatible native,
web,function and per-card rollback targets remain unfilled execution holds. Local
[selective-compensation qualification](D13A-following-rollback-20261011.md) is retained;
it is not a deployed operator or proof of live queue reconciliation.

## Invariants and stop conditions

Preserve personal IDs,owners,collections,raw originals,all accepted reviews/resets/
corrections,SRS and unsent queues. Never restore an old whole personal/device database
as routine rollback,rewind a cursor/content version,delete an unknown paid liability,
blindly redispatch,drop additive schema or clear conflicting queues. The QA database
restore used in D13A.7 is synthetic evidence and is explicitly excluded from live recovery.

Stop expansion immediately on any ownership/privacy leak,unapproved content publication,
lost/duplicated learning,missing dependency acknowledged as fresh,unexpected function/
migration/profile/role change,unknown paid outcome or spending limit breach. A sustained

> 10% latency investigation trigger uses comparable samples; it is not a new universal
> SLA. Retain the D13A.7 cache-load cost and observed tail when assessing new regressions.
> Capture exact operation/artifact IDs,cursors/head sequences,count/digest deltas and logs
> before intervention. Touch only the affected release resources/cohort.

## Containment and reconciliation order

1. Stop only the owned apply/dispatch workers for the exact run. Stop accepting new paid
   work through the new endpoint/operation/dispatch gates; preserve existing v1 reads,
   following reads,learning delivery and legacy guards. Do not use global read-disable
   as a substitute for repair. Record in-flight operation IDs,leases/fences,durable
   result hashes and unknown statuses. Retain unknown quota/cost reservations.
2. Drain or explicitly reconcile durable in-flight work before re-enabling any publisher.
   A result already received can be recovered from its journal without paying again.
   Revoking new dispatch alone does not prove a late response cannot publish; verify
   the actual fencing/status/publication gate behavior and record each outcome.
3. Select the scenario below and obtain the matching exact authority. Expected-head or
   per-card fingerprint conflict becomes a hold,new review and new operation as required;
   it is not permission to overwrite a newer result.
4. Verify complete preservation and delivery after compensation/forward repair. Resume
   only after a fresh reviewed compatible packet,not after an arbitrary timer expires.

## Exact shared-head command contract

The implemented RPC expects protocol_version2,operation_id,entry_id,expected_revision_id,
expected_head_sequence as a decimal string,target_revision_id and a bounded reason.
It checks current trusted administrator membership independently of normal full_access.
The target must be a published revision of the same entry. Moving to older content
creates a **newer global delivery sequence**; never restore an old sequence value.
An exact retry returns the saved receipt; a changed payload with the same UUID fails.
Later shared heads and head ABA require fresh review. A repair must not remove accepted
reviews or replace personal rows. No concrete live IDs are invented in this plan.

## Selective link compensation contract

The existing administrator rehearsal schema is not installed in production by this plan.
A later approved live operator must preserve the tested contracts before use. Stop
outstanding apply workers first; compensating committed receipts does not cancel other
uncommitted work. Bind run_id,exact reviewed plan SHA256,new batch UUID and limit50
(default;hard maximum100). Compensate only committed applied receipts whose complete
current result fingerprint and approved head/sequence still match. Restore only owned
reference/mode/fallback/override state with a new monotonic content version. Preserve
later SRS/review/reset/correction,raw content,collection/owner/deletion and all queues.

Changed reference/content/placement,deleted rows,changed owner,new shared head or ABA,
version exhaustion and unknown queues are reconciliation holds. Missing original state
becomes the preserved protected legacy fallback at the new version; never version0.
Committed exact batch retry returns its durable receipt. Busy rows need a fresh batch
UUID after the lock clears; do not reinterpret a committed batch or change its limit.
Deliver the authoritative compensation through existing sync/cursor machinery; do not
copy the old SQLite backup to a real device. Require actual returning-device acceptance
for the final live package before broad linking.

## Native update and database limitations

Expo runtimeVersion uses exact matching; channel/branch/request filters also matter.
Republishing an earlier group and an embedded rollback are publication operations.
Channel pause leaves clients on their current update and does not repair installed data.
Neither operation rolls back SQLite or server writes. Native code/schema and pending
commands must remain compatible. Embedded85 had repaired parser/queue constraints;
there is no approved default embedded rollback for the new following release. Do not
run a generic rollback-to-embedded or assume an old update can consume new local state.

Record per-platform current and target production update-group/runtime/asset hashes and
verify their original signed/native delivery path. If native dependencies/fingerprint
changed,an OTA cannot substitute for a compatible native build. Store distribution
changes/TestFlight/internal delivery remain separately scoped operations. Rollback
must never implicitly enable CEFR or invoke the paid provider.
